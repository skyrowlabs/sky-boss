# Job management — `tb auto`

## Why

This is what the repo is for. Everything built so far — the output contract, the asset register,
the drift check — produces answers that nobody is around to read. A job runner is what turns
`tb assets update` from something you remember to type into something that tells you when a
machine changed.

The specific gap it closes is visible in jam.sense's crontab on this machine. Those ~24 entries
carry comments like *"03:45 is a scheduling constraint, not a preference"*, *"this must not
overlap a committing job"*, and *"the evening slots are not free"*. **Those are mutexes written in
prose, enforced by nothing.** The constraint is real and was learned expensively; the only thing
preventing a violation is remembering to read the comments before adding a line.

Long jobs also need somewhere to live. A 45-minute agentic run must not die with the terminal,
must be inspectable afterwards, and must not silently overlap something it conflicts with.

**This manages homebase jobs only.** jam.sense keeps its own scheduler — see CLAUDE.md § Boundary.

## Shape

**Substrate: systemd user units and timers, generated by `tb`.** Not cron, not a hand-rolled
scheduler. Verified on workstation: the user manager is running and `systemd-run --user` works. It
provides journal logging, exit-status tracking, timeouts, restart policy, detachment surviving
logout, and calendar scheduling that is validated by `systemd-analyze calendar` rather than by a
parser of ours.

**Lanes are enforced by `tb`, not by systemd.** `Conflicts=` was the original plan and is wrong:
it *stops* the conflicting unit rather than waiting or refusing, which is preemption, not mutual
exclusion — a scheduled job would kill a running one. Instead `tb auto run` takes an advisory
`flock` on a per-lane file in `$XDG_RUNTIME_DIR`, and a job that cannot get it records a
`skipped` outcome. One mechanism, and it protects manual runs too, which a unit directive never
would.

`tb` generates and inspects units; it does not reimplement a scheduler. The same relationship
`bbrain` has to Docker.

**Job definitions are declarative and live in the repo**, under `jobs/*.yaml` — versioned, so the
schedule has a source and the git diff says why it changed:

```yaml
name: asset-drift
description: Re-derive workstation and report drift against its record
run: [tb, assets, update]
lane: read-only          # read-only | committing
timeout: 300
schedule: daily 06:00    # optional; absent means manual only
```

**Exit codes are the interface, and this is where the output contract pays off.** `0` ok, `1`
failed, `3` partial. A job exiting 3 means *something needs attention* without anything having to
parse output — which is precisely why `partial` got its own code back in `output-contract`.

**The ledger is durable and lives outside the repo**, at `~/.local/state/tb/jobs/`: what ran,
when, exit status, duration, log path. A gitignored directory in the repo is what `git clean -xdf`
destroys, and run history is the thing you least want to lose.

**With no notifier, the log is the notification surface** — so it is not a later phase and not a
debugging artifact. It is written from the very first run, and reading it has to be a single
command that answers "what happened, and does anything need me". A log you have to `grep` is a log
you stop checking, which is the same outcome as having no log at all.

### Rules that are not negotiable

- **`tb` only ever touches units it generated.** Every generated unit is named `tb-<job>.service`
  / `tb-<job>.timer`. This machine already has foreign user units — `arch-update.timer` and
  `openclaw-gateway.service` — and tb must never enumerate, modify, or stop anything outside its
  own prefix.
- **The crontab is read-only.** jam.sense's entries are derived as reserved windows and never
  written, reordered, or removed. Collision avoidance is **advisory at schedule time**: systemd
  `Conflicts=` only mutexes between units, and cron jobs are not units.
- **Nothing runs on a schedule until you install it.** Generating a unit and enabling a timer are
  separate steps.
- **A job that produces no log did not run.** Every execution appends to the ledger, including
  failures and refusals.

**Does not do:**

- **No jam.sense job management.** Not its cron, not its schedule, not its lanes.
- **No remote execution.** Jobs run on this machine. Targeting other hosts needs
  [[asset-remote]].
- **No daemon of its own.** systemd is the daemon.
- **No retry or backoff in v1.** A failed job is reported, not re-run. Retries hide flapping.
- **No notification transport in v1** — delivery (desktop, Slack, push) is a later phase, and
  picking one badly is worse than not having it. **The log replaces it, so the log has to be good
  enough to be checked deliberately.** That obligation is Phase 2 and is not optional.
- **No job authoring by agents.** An agentic *job* is a job whose `run` invokes Claude. Agents do
  not write or install job definitions.

## Phases

### Phase 1 — Definitions, runs, and the ledger

Nothing here runs unlogged. There is no phase during which jobs execute without a record.

- [x] `jobs/*.yaml` schema: name, description, run, lane, timeout, optional schedule
- [x] Loader with validation; a malformed definition names the file and the problem
- [x] `tb auto list` — every job with lane, schedule and whether it is installed
- [x] `tb auto run <job>` — run in the foreground, honouring timeout
- [x] Job exit code is surfaced, not swallowed: 0 ok, 1 failed, 3 partial
- [x] Every run appends to `~/.local/state/tb/jobs/ledger.jsonl` — including failures, timeouts
      and refusals to start
- [x] Per-run output captured to its own log file beside the ledger
- [x] Ledger append survives a run killed mid-write (append-only, one JSON object per line)
- [x] `jobs/_template.yaml`

### Phase 2 — Reading the log

This is the notification surface. It stands in for delivery, so it has to answer the question a
notification would have answered, in one command.

- [x] `tb auto status` — last outcome per job, worst first, using the `ok` convention so failures
      and partials are visually obvious
- [x] `tb auto log <job>` — that job's recent runs, most recent first, with duration and exit
- [x] `tb auto log <job> --run <id>` — the captured output of one run
- [x] `tb auto since <duration>` — everything across all jobs in a window, e.g. `24h`. The
      "what happened overnight" view
- [x] A job that has never run reads as never-run, not as passing
- [x] A job whose schedule was missed reads as overdue, not as passing — silence must never look
      like success
- [x] Retention: cap per-run logs and prune the ledger, so the surface stays readable and does not
      grow without bound

### Phase 3 — Scheduling

- [x] Generate `tb-<job>.service` and `tb-<job>.timer` into `~/.config/systemd/user/`
- [x] `tb auto install <job>` / `tb auto uninstall <job>`; never touches non-`tb-` units
- [x] Lanes enforced by an advisory `flock` per lane, recorded as a `skipped` outcome
- [x] `tb auto install` is explicit — generating never enables
- [x] Schedules translate to `OnCalendar` and are validated by `systemd-analyze calendar`
- [x] Test asserting a generated unit never references a unit outside the `tb-` prefix

### Phase 4 — Reserved windows

- [x] Parse `crontab -l`, treating every entry tb did not generate as an opaque busy window
- [x] Warn at schedule time when a job lands in a reserved window
- [x] Never write to the crontab
- [x] Optional runtime guard: skip if a `jam report` process is currently running

### Phase 5 — First real jobs

- [x] `asset-drift` — `tb assets update`, daily
- [x] `unpushed-audit` — uncommitted or unpushed work across `~/src`
- [x] `doctor` — auth expiry sweep
- [x] Each lands as a `jobs/*.yaml`, not as Python

## Notes

Jobs are the first consumer that makes the exit-code contract load-bearing rather than tidy. A
job wrapper that had to parse output to decide whether something needs attention would be the
signal that the contract was wrong.

**Deferring the notifier puts the whole burden on the log**, so two failure modes matter more than
they otherwise would: a job that never ran must not read as passing, and a job that missed its
schedule must not read as passing. Silence looking like success is the specific way a pull-based
surface fails, and it is worse than no surface at all because it is quietly reassuring.

The three jobs in Phase 5 are drawn from `docs/jobs-backlog.md`, which stays the pool. Only
promote a job when it is next.

`arch-update.timer` already exists on this machine as a foreign user timer. It is a useful
reminder that `~/.config/systemd/user/` is shared space, not tb's directory.

**Phase 1 (2026-08-18).** Four outcomes, not two: `ok`, `partial`, `failed`, plus **`timeout`** and
**`refused`** (the binary could not start). Both of the latter are *recorded outcomes, not
exceptions* — with the ledger standing in for a notifier, a run that vanished without a line is
indistinguishable from one that never happened.

`run` must be an **argv list**, and a shell string is a validation error. Accepting
`tb doctor | grep x` would mean every job silently gains a shell, with its globbing, quoting and
injection surface, for no benefit.

**A malformed definition does not hide the others.** `load_jobs` returns what parsed plus one
message per file that failed, each naming the file and the problem. One bad job taking down the
whole schedule is the failure mode of a loader that raises.

`tb auto run` **mirrors the job's exit code** — 0, 3, 1 — so a wrapper can branch on it without
parsing anything. This is the first place the output contract's `partial` code does real work
rather than being tidy.

The log tail is a newline-joined **string**, not a list. The renderer joins a list of strings with
commas, which turns captured output into an unreadable blob; newlines are what log output is.

`jobs/asset-drift.yaml` and `jobs/doctor.yaml` are the first two definitions. Live: `tb auto run
doctor` exited 3 with `bws` unauthenticated, wrote its ledger line and its own log file.

**Phase 2 (2026-08-18).** `tb auto status` is the command that stands in for a notification, and
the two traps it exists to avoid both have tests:

- **A job that has never run reads as `never run` with no verdict** (`ok: None`, a muted `·`) —
  not as passing.
- **A scheduled job whose window has passed reads as `overdue`**, even when its last run
  succeeded. A stale success is still a failure to run.

Rows sort **worst first** by an explicit severity table: failed/timeout/refused, then overdue,
partial, never, ok. The point of a pull surface is that the thing needing attention is the first
thing you see.

Overdue uses a generous 1.5× the schedule period. A job flagged overdue an hour early is noise,
and noise is how a pull surface gets ignored. The real schedule parser is Phase 3; this reads the
`hourly`/`daily`/`weekly`/`monthly` prefix and declines to guess at anything else.

`read_ledger` **skips malformed lines rather than raising** — the truncated-last-line case the
append-only format was chosen to survive. One bad line must not cost the history before it.

`tb auto prune` is **explicit, never automatic**. Quietly deleting the surface that stands in for
notification, on a schedule nobody asked for, is how it loses the run you needed. It is a good
candidate for a scheduled job later, which is a decision made in a `jobs/*.yaml` you can read.

The status footer gained an `unknown` count in `cli/output.py`: rows with no verdict were being
dropped from the tally, so a 3-row list reported "1 passed 1 failed" and silently lost the third.

**Phase 3 (2026-08-18).** **`Conflicts=` was the wrong mechanism and the spec was corrected before
building.** systemd's `Conflicts=` *stops* the conflicting unit — a scheduled job would kill a
running one. That is preemption, not mutual exclusion.

Lanes are now an advisory `flock` on a per-lane file in `$XDG_RUNTIME_DIR`, taken by `tb auto run`
itself. Three consequences, all better than the unit directive would have been:

- It protects **manual** runs too, which a unit directive never could.
- A blocked job records a **`skipped`** outcome instead of dying. Non-blocking on purpose: a job
  that waits its turn silently is a job whose schedule is now a lie.
- The lock lives on tmpfs, so a crash cannot leave a stale file that wedges a lane forever.

`skipped` is neither pass nor fail in `tb auto status` — the lane being held is the mutex working.

Schedules translate to `OnCalendar` and are then **validated by `systemd-analyze calendar`**.
Calendar syntax is systemd's to define; a parser of ours would drift from it.

`ExecStart` resolves an **absolute** program path at install time. systemd user units get a
minimal PATH that excludes `~/.local/bin`, so a bare `tb` would simply not be found at 6am with
nobody watching. A missing program fails at install rather than at run time.

`Persistent=true` on the timer: a missed daily job runs once the machine is back rather than
silently skipping the day — this is a workstation, not a server.

Live: `tb-log-prune.timer` is installed and registered, next elapse Sun 09:00. `arch-update.timer`
and `openclaw-gateway.service` are untouched, and there is a test asserting generated units
reference nothing outside the `tb-` prefix.

**Phase 4 (2026-08-18).** All 24 of jam.sense's crontab entries parse; none were unreadable.
Unparseable entries are *surfaced* rather than dropped, because silently ignoring one would claim
coverage this does not have.

**The collision check immediately caught its author.** Scheduling `asset-drift` at 07:15 looked
safe — jam.sense's overnight spine runs 03:15 to 06:30 — but `jam report release` runs
`20 3,7,11,15,19,23 * * *`, so every fourth hour at twenty past. Exactly the class of mistake the
crontab comments describe and nothing enforced. Only seven daily half-hour slots are clear of
everything; `asset-drift` now runs at 09:00 and reports 0 collisions.

Collision warning is **advisory and does not block installation**. systemd cannot mutex against
cron because cron jobs are not units, so a warning at schedule time is the entire mechanism.

The runtime guard is implemented over `/proc`, **not** `pgrep -f`, and excludes this process and
its ancestors. Verified on this machine: `pgrep -f 'jam report'` reported a match when nothing of
the sort was running, because the checking shell's own command line contained the pattern. A guard
that always fires is worse than no guard.

`avoid:` is a per-job list of command-line fragments. A job that matches one records `skipped`
rather than running — the only guard tb can apply unilaterally against another project's cron.

**Phase 5 (2026-08-18).** Four jobs installed and enabled: `unpushed-audit` 08:30, `asset-drift`
09:00, `doctor` 12:00, `log-prune` Sunday 09:00. All report 0 collisions against jam.sense's
crontab.

`tb unpushed` was the one new command this phase needed. It scans `~/src`, which brushes
against the project-orchestration domain deliberately left out of scope — it earns its place by
asking a **data-risk** question rather than a project one, and must not grow into acting on repos.

Its first run found real exposure: `breeze.brain` 1 unpushed commit, `mind-head` 2, `house.fly`
uncommitted work, and **`tackle-box` itself with no remote at all**. The job that checks whether
work lives on one disk immediately flagged the repo containing it.

A remote with no upstream branch counts as exposed. A remote nothing tracks is not a backup.

Repo discovery is deliberately shallow — a repo nested inside a checkout is usually a vendored
dependency, not work.
